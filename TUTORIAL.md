# Tutorial: add a feature, remove a feature

A hands-on walkthrough in two parts. Part 1 builds a complete new resource — **Suppliers** —
through every layer, backend to nav link. Part 2 is the reverse: recipes for cleanly removing
the demo features you don't need, with verification steps so nothing dangles.

Prerequisite: the app running per the [README](README.md) quickstart (any path — native or
Docker). Sign in as `admin` / `password` so you can exercise what you build.

This document is the *how*; [docs/02-adding-a-secure-feature.md](docs/02-adding-a-secure-feature.md)
is the *how to not leave a security hole while doing it*. Read that one before shipping
anything real.

---

## Part 1 — Add a feature: Suppliers, end to end

We'll add a "Suppliers" resource: companies that sell parts to your facilities. Fields: name,
contact email, active flag. Reads for every signed-in business role, writes for Admin only.
Every step ends with something you can run or click.

### Step 0 — decide the access rule first

Ours: `Admin, Inspector, Viewer` may read; `Admin` may write. We're reusing existing roles —
if your feature needs a *new* role, do
[docs/02 Step 2](docs/02-adding-a-secure-feature.md#step-2---does-this-need-a-new-role) first.

### Step 1 — migration

Migrations are append-only and numbered. Find the highest `V<n>` in
`backend/src/main/resources/db/migration/` and go one higher. As of this writing that's V5,
so create `backend/src/main/resources/db/migration/V6__suppliers.sql`:

```sql
create table supplier (
    id              bigint generated by default as identity primary key,
    name            varchar(200) not null unique,
    contact_email   varchar(254) not null,
    active          boolean      not null default true,
    created_at      timestamp    not null default current_timestamp,
    updated_at      timestamp    not null default current_timestamp
);

-- A couple of demo rows so the page isn't empty on first run
insert into supplier (name, contact_email, active) values
    ('Acme Gears & Sprockets', 'sales@acmegears.example', true),
    ('Widget Wholesale Co.', 'orders@widgetwholesale.example', true);
```

Flyway applies it on next startup. The dev database is in-memory H2, so every restart
rebuilds from scratch — you can iterate on this file freely until it's deployed somewhere
real, after which it's frozen and changes mean a new `V7`.

### Step 2 — entity

`backend/src/main/java/com/example/bffkickstart/models/Supplier.java` — copy the shape of
`Facility.java`, which is the template for every entity here (Lombok accessors,
`@PrePersist`/`@PreUpdate` timestamps):

```java
package com.example.bffkickstart.models;

import jakarta.persistence.*;
import lombok.Getter;
import lombok.NoArgsConstructor;
import lombok.Setter;

import java.time.Instant;

@Entity
@Table(name = "supplier")
@Getter
@Setter
@NoArgsConstructor
public class Supplier {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 200)
    private String name;

    @Column(name = "contact_email", nullable = false, length = 254)
    private String contactEmail;

    @Column(nullable = false)
    private boolean active = true;

    @Column(name = "created_at", nullable = false, updatable = false)
    private Instant createdAt;

    @Column(name = "updated_at", nullable = false)
    private Instant updatedAt;

    @PrePersist
    void onCreate() {
        Instant now = Instant.now();
        createdAt = now;
        updatedAt = now;
    }

    @PreUpdate
    void onUpdate() {
        updatedAt = Instant.now();
    }
}
```

### Step 4 — DTOs

Two per resource: a request with Bean Validation (the server-side half of the validation
story — the frontend zod schema in Step 8 mirrors it), and a response with a `from()` mapper.

`dtos/SupplierRequest.java`:

```java
package com.example.bffkickstart.dtos;

import jakarta.validation.constraints.Email;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;
import lombok.Getter;
import lombok.Setter;

@Getter
@Setter
public class SupplierRequest {

    @NotBlank(message = "Name is required")
    @Size(max = 200, message = "Name must be at most 200 characters")
    private String name;

    @NotBlank(message = "Contact email is required")
    @Email(message = "Contact email must be a valid email address")
    @Size(max = 254, message = "Contact email must be at most 254 characters")
    private String contactEmail;

    private boolean active = true;
}
```

`dtos/SupplierResponse.java`:

```java
package com.example.bffkickstart.dtos;

import com.example.bffkickstart.models.Supplier;
import lombok.Builder;
import lombok.Getter;

import java.time.Instant;

@Getter
@Builder
public class SupplierResponse {
    private Long id;
    private String name;
    private String contactEmail;
    private boolean active;
    private Instant createdAt;
    private Instant updatedAt;

    public static SupplierResponse from(Supplier s) {
        return SupplierResponse.builder()
                .id(s.getId())
                .name(s.getName())
                .contactEmail(s.getContactEmail())
                .active(s.isActive())
                .createdAt(s.getCreatedAt())
                .updatedAt(s.getUpdatedAt())
                .build();
    }
}
```

### Step 5 — service

`services/SupplierService.java`. Business rules live here — controllers stay thin. Note the
`ConflictException` on duplicate names: `GlobalExceptionHandler` turns it into a 409 with the
app's uniform error JSON, and the frontend toasts the message as-is.

```java
package com.example.bffkickstart.services;

import com.example.bffkickstart.dtos.PageResponse;
import com.example.bffkickstart.dtos.SupplierRequest;
import com.example.bffkickstart.dtos.SupplierResponse;
import com.example.bffkickstart.exceptions.ConflictException;
import com.example.bffkickstart.exceptions.NotFoundException;
import com.example.bffkickstart.models.Supplier;
import com.example.bffkickstart.repositories.SupplierRepository;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
@Transactional
public class SupplierService {

    private final SupplierRepository supplierRepository;

    public SupplierService(SupplierRepository supplierRepository) {
        this.supplierRepository = supplierRepository;
    }

    @Transactional(readOnly = true)
    public PageResponse<SupplierResponse> search(String q, Pageable pageable) {
        Page<Supplier> page = (q == null || q.isBlank())
                ? supplierRepository.findAll(pageable)
                : supplierRepository.findByNameContainingIgnoreCase(q.trim(), pageable);
        return PageResponse.of(page, SupplierResponse::from);
    }

    @Transactional(readOnly = true)
    public SupplierResponse getById(Long id) {
        return SupplierResponse.from(getEntity(id));
    }

    public SupplierResponse create(SupplierRequest request) {
        if (supplierRepository.existsByNameIgnoreCase(request.getName())) {
            throw new ConflictException("A supplier named '%s' already exists".formatted(request.getName()));
        }
        Supplier supplier = new Supplier();
        apply(supplier, request);
        return SupplierResponse.from(supplierRepository.save(supplier));
    }

    public SupplierResponse update(Long id, SupplierRequest request) {
        Supplier supplier = getEntity(id);
        if (!supplier.getName().equalsIgnoreCase(request.getName())
                && supplierRepository.existsByNameIgnoreCase(request.getName())) {
            throw new ConflictException("A supplier named '%s' already exists".formatted(request.getName()));
        }
        apply(supplier, request);
        return SupplierResponse.from(supplier);
    }

    public void delete(Long id) {
        supplierRepository.delete(getEntity(id));
    }

    private Supplier getEntity(Long id) {
        return supplierRepository.findById(id)
                .orElseThrow(() -> new NotFoundException("Supplier %d not found".formatted(id)));
    }

    private void apply(Supplier supplier, SupplierRequest request) {
        supplier.setName(request.getName().trim());
        supplier.setContactEmail(request.getContactEmail().trim());
        supplier.setActive(request.isActive());
    }
}
```

### Step 6 — controller

`controllers/SupplierController.java`. This is where the access rule from Step 0 becomes
real. Class-level `@PreAuthorize` is the read default; write methods override it. The
`@ParameterObject` on `Pageable` makes Swagger render proper `page`/`size`/`sort` params.

```java
package com.example.bffkickstart.controllers;

import com.example.bffkickstart.dtos.PageResponse;
import com.example.bffkickstart.dtos.SupplierRequest;
import com.example.bffkickstart.dtos.SupplierResponse;
import com.example.bffkickstart.services.SupplierService;
import jakarta.validation.Valid;
import org.springdoc.core.annotations.ParameterObject;
import org.springframework.data.domain.Pageable;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.security.access.prepost.PreAuthorize;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/v1/suppliers")
@PreAuthorize("hasAnyRole('Admin','Inspector','Viewer')")
public class SupplierController {

    private final SupplierService supplierService;

    public SupplierController(SupplierService supplierService) {
        this.supplierService = supplierService;
    }

    @GetMapping
    public PageResponse<SupplierResponse> search(@RequestParam(required = false) String q,
                                                  @ParameterObject Pageable pageable) {
        return supplierService.search(q, pageable);
    }

    @GetMapping("/{id}")
    public SupplierResponse getById(@PathVariable Long id) {
        return supplierService.getById(id);
    }

    @PostMapping
    @PreAuthorize("hasRole('Admin')")
    public ResponseEntity<SupplierResponse> create(@Valid @RequestBody SupplierRequest request) {
        return ResponseEntity.status(HttpStatus.CREATED).body(supplierService.create(request));
    }

    @PutMapping("/{id}")
    @PreAuthorize("hasRole('Admin')")
    public SupplierResponse update(@PathVariable Long id, @Valid @RequestBody SupplierRequest request) {
        return supplierService.update(id, request);
    }

    @DeleteMapping("/{id}")
    @PreAuthorize("hasRole('Admin')")
    public ResponseEntity<Void> delete(@PathVariable Long id) {
        supplierService.delete(id);
        return ResponseEntity.noContent().build();
    }
}
```

### Step 7 — checkpoint: prove the backend before touching the frontend

Restart the backend (`mvn spring-boot:run`, or `docker compose up -d --build backend` — and
if you're on the Docker path, `docker compose restart frontend` afterwards so nginx
re-resolves the rebuilt container). Then:

1. Sign in to the app as `admin`, then hit
   `http://localhost:5173/bff-kickstart/api/v1/suppliers` directly in the same browser —
   you should get JSON with the two demo rows.
2. If Swagger is on (`SWAGGER_ENABLED=true`), open the API docs: `supplier-controller`
   appears with a **Requires role:** line on every operation — generated from the
   `@PreAuthorize` you just wrote, no annotations needed.
3. Sign out, sign in as `viewer` / `password`, and try a create via Swagger or curl — expect
   the 403 JSON. *The backend rule is the security; everything after this step is UX.*

### Step 8 — frontend: types with a zod schema

Frontend features are self-contained modules under `frontend/src/features/<name>/` with a
fixed internal shape: `components/`, `hooks/`, `api/`, `types/`, and an `index.ts` that is
the feature's only public surface.

`frontend/src/features/suppliers/types/supplier.ts` — the zod schema mirrors Step 4's Bean
Validation so users see errors before the round-trip, not instead of it:

```ts
import { z } from 'zod';

export const supplierSchema = z.object({
  name: z.string().trim().min(1, 'Name is required').max(200, 'Name must be at most 200 characters'),
  contactEmail: z
    .string()
    .trim()
    .min(1, 'Contact email is required')
    .email('Contact email must be a valid email address')
    .max(254, 'Contact email must be at most 254 characters'),
  active: z.boolean(),
});

export type SupplierFormValues = z.infer<typeof supplierSchema>;

export interface SupplierResponse {
  id: number;
  name: string;
  contactEmail: string;
  active: boolean;
  createdAt: string;
  updatedAt: string;
}
```

### Step 9 — frontend: api + hooks

`api/suppliers.ts` — thin functions over the shared `apiClient` (which already handles the
session cookie, CSRF header, and 401s):

```ts
import { apiClient, type Page } from '../../../lib/api-client';
import type { SupplierFormValues, SupplierResponse } from '../types/supplier';

export interface SupplierSearchParams {
  q?: string;
  page: number;
  size: number;
  sort?: string;
}

export async function fetchSuppliers(params: SupplierSearchParams): Promise<Page<SupplierResponse>> {
  const { data } = await apiClient.get<Page<SupplierResponse>>('/suppliers', { params });
  return data;
}

export async function createSupplier(values: SupplierFormValues): Promise<SupplierResponse> {
  const { data } = await apiClient.post<SupplierResponse>('/suppliers', values);
  return data;
}

export async function updateSupplier(id: number, values: SupplierFormValues): Promise<SupplierResponse> {
  const { data } = await apiClient.put<SupplierResponse>(`/suppliers/${id}`, values);
  return data;
}

export async function deleteSupplier(id: number): Promise<void> {
  await apiClient.delete(`/suppliers/${id}`);
}
```

`hooks/useSuppliers.ts` — TanStack Query wrappers; components never touch axios directly:

```ts
import { keepPreviousData, useMutation, useQuery, useQueryClient } from '@tanstack/react-query';
import { createSupplier, deleteSupplier, fetchSuppliers, updateSupplier, type SupplierSearchParams } from '../api/suppliers';
import type { SupplierFormValues } from '../types/supplier';

export function useSuppliers(params: SupplierSearchParams) {
  return useQuery({
    queryKey: ['suppliers', params],
    queryFn: () => fetchSuppliers(params),
    placeholderData: keepPreviousData,
  });
}

export function useCreateSupplier() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: (values: SupplierFormValues) => createSupplier(values),
    onSuccess: () => queryClient.invalidateQueries({ queryKey: ['suppliers'] }),
  });
}

export function useUpdateSupplier(id: number) {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: (values: SupplierFormValues) => updateSupplier(id, values),
    onSuccess: () => queryClient.invalidateQueries({ queryKey: ['suppliers'] }),
  });
}

export function useDeleteSupplier() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: (id: number) => deleteSupplier(id),
    onSuccess: () => queryClient.invalidateQueries({ queryKey: ['suppliers'] }),
  });
}
```

### Step 10 — frontend: page and form, by adaptation

Don't write these from scratch — the facilities feature is the intended template. Copy and
trim:

- `components/SupplierForm.tsx` ← copy `features/facilities/components/FacilityForm.tsx`.
  Keep the skeleton (`useForm` + `zodResolver`, `FormErrorSummary`, `useApplyServerErrors`,
  the Cancel/Save footer). Replace the fields with two `TextInputField`s (`name`,
  `contactEmail`) and the `CheckboxField` (`active`); delete the facility-type select, the
  address grid, and the whole Location fieldset.
- `components/SuppliersPage.tsx` ← copy `features/facilities/components/FacilitiesPage.tsx`.
  Keep the structure (search input, `DataTable`, create/edit `Modal`, `ConfirmDeleteDialog`).
  Swap in your hooks and columns (`name`, `contactEmail`, an `active` chip), and set
  `canEdit = hasRole('Admin')` — matching Step 6's write rule, because a button the backend
  would 403 is worse than no button. Drop the type/status filters and `BulkActions` unless
  you want CSV import/export (then mirror the facilities CSV endpoints on the backend too).

### Step 11 — public surface + one line in the route table

`frontend/src/features/suppliers/index.ts`:

```ts
import type { AppRoute } from '../../lib/appRoute';
import { SuppliersPage } from './components/SuppliersPage';

export { SuppliersPage } from './components/SuppliersPage';

export const suppliersRoute: AppRoute = {
  path: '/suppliers',

```

Then in `frontend/src/app-routes.ts`, import `suppliersRoute` and add it to `APP_ROUTES` in
the position you want it in the nav. That single line is the whole registration: `App.tsx`
turns the list into routes, `AppShell.tsx` turns it into nav links (desktop and the mobile
menu both), and the auth guard applies by default.

### Step 12 — verify like you mean it

- `cd frontend && npx tsc -b --noEmit` — clean.
- "Suppliers" appears in the nav; the page lists the two demo rows; create/edit/delete work
  as `admin` with toasts on success and a useful message on a duplicate name.
- As `viewer`: page renders read-only (no buttons) — and the API still 403s a hand-made
  POST, which you proved in Step 7 before the UI existed.
- Both pagination directions work once you add an 11th supplier.

Done. One migration, five backend files, five frontend files, one route-table line.

## Part 2 — Remove features you don't need

The demo domain exists to be deleted. Each recipe below lists what to remove, what to edit,
and how to prove nothing dangles. The general method, which works for anything not listed:

1. Delete the frontend feature directory and its `app-routes.ts` line first (the app stays
   shippable at every step this way).
2. Delete the backend slice: controller → service → repository → entity/DTOs.
3. Grep for the feature's names until clean:
   `grep -rniE "supplier" --include="*.java" --include="*.ts*" backend/src frontend/src`
4. Rebuild both sides: `mvn -q clean package -DskipTests` and `npx tsc -b --noEmit` — the
   compilers find what grep's spelling missed.
5. Data: dev H2 is wiped every restart, so editing seed/migration files is safe *until
   you've deployed against a persistent database* — after that, write a new `V<n>` migration
   with the `drop table`, never edit an applied one.

### Remove Daily Reports (and the whole second datasource)

The read-only warehouse view exists to demonstrate the two-datasource pattern. If you don't
need it, it takes the entire second JPA stack with it:

- **Delete** `frontend/src/features/daily-reports/`; remove `dailyReportsRoute` (import +
  list entry) from `app-routes.ts`.
- **Delete** the whole `backend/src/main/java/com/example/bffkickstart/reporting/` package —
  controller, service-less repository, entity, DTO, and `ReportingDataSourceConfig` (the
  second `HikariDataSource`/`EntityManagerFactory`/Flyway).
- **Delete** `backend/src/main/resources/db/migration-rpt/`.
- **Edit** `application.properties`: remove the `db.kickstart-rpt.*` block.
- **Verify**: `grep -rniE "daily.?report|kickstart-rpt|kickstartRpt" backend/src frontend/src`
  → nothing; both builds clean; home page still loads (its counts don't touch this data).

### Remove the email demo

- **Delete** `frontend/src/features/home/components/SendMailModal.tsx` and the "Send Email"
  button/modal usage in `HomePage.tsx`.
- **Delete** `controllers/MailController.java`, `services/MailService.java`,
  `dtos/MailRequest.java`.
- **Edit** `GlobalExceptionHandler` (drop the `MailException` handler + import),
  `application.properties` (the `spring.mail.*` / `app.mail.from` block), `pom.xml`
  (`spring-boot-starter-mail`), `docker-compose.yml` (the `mailhog` service and the
  backend's `SMTP_*` env lines), `.env.example` (`SMTP_*`).
- **Verify**: `grep -rniE "mail|smtp" backend/src frontend/src docker-compose.yml` — expect
  only unrelated hits (e.g. "email" in Keycloak user fields); builds clean.
- Note: the local Keycloak stand-in's own SMTP block (`keycloak/realm-export/*.json`,
  "forgot password" emails) is independent — keep or remove separately.

### Remove compliance reports (CSV/PDF)

- **Delete** `frontend/src/features/reports/`; remove `reportsRoute` from `app-routes.ts`.
- **Delete** `controllers/ReportController.java`, `services/ReportService.java`,

- **Edit** `pom.xml`: drop `com.github.librepdf:openpdf` (keep `commons-csv` — the bulk

- **Verify**: `grep -rniE "compliance|openpdf|lowagie" backend/src frontend/src` → nothing.

### Remove inspection attachments

- **Edit** `frontend/src/features/inspections/components/InspectionsPage.tsx`: remove the

- **Delete** `components/InspectionAttachments.tsx`, `hooks/useInspectionAttachments.ts`,

- **Delete** `controllers/InspectionAttachmentController.java`,

  `drop table inspection_attachment;`

### Remove facility location capture

- **Edit** `FacilityForm.tsx`: delete the Location fieldset, the geolocation handlers, and

- **Verify**: `grep -rniE "latitude|longitude|locationSource|geolocation" backend/src frontend/src`.

### Remove the PWA layer

- **Edit** `frontend/vite.config.ts`: remove the `VitePWA(...)` plugin block and its import;
  `frontend/index.html`: remove the `theme-color` meta and `apple-touch-icon` link;
  `package.json`: drop `vite-plugin-pwa`.
- **Delete** `frontend/public/pwa-icon-*.png`, `pwa-maskable-512.png`.
- Users who already installed it keep a cached shell until their browser refreshes the
  (now-absent) service worker; that resolves itself.

### Remove Swagger entirely

It's already **off by default** (`SWAGGER_ENABLED=false`) — most teams should stop there.
To excise it: delete `configurations/SwaggerBrandingConfig.java`,
`configurations/SwaggerRolesConfig.java`, `src/main/resources/swagger/`; drop the springdoc
dependency from `pom.xml` and the `springdoc.*` lines from `application.properties`; remove
the swagger `location` blocks from `frontend/nginx.conf.template` and the swagger paths from
`vite.config.ts`'s proxy regex; remove the docs-tier rules (`/v3/api-docs`, `/swagger-ui`)
from `SecurityConfig` — and retire the `API Developer` / `API Owner` roles in your realm if
nothing else uses them.

### What not to remove

`SecurityConfig`, the session/CSRF machinery, `KeycloakRealmRoleConverter`, `MeController`,
the axios interceptor, and the proxy configs are the product. Everything above is furniture.
